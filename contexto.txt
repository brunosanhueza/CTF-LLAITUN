--------------------------------------------------------------------------------
1. QUÉ ES ESTA WEA Y LA EVOLUCIÓN DEL PROYECTO
--------------------------------------------------------------------------------
Este proyecto es una máquina / entorno simulado para un Capture The Flag (CTF) IT/OT de alto nivel. La idea central es simular la red corporativa y la red industrial de "Aguas del Valle S.A.". 

El CTF no es solo web; mezcla Web Hacking, Criptografía Básica, Fuzzing de Directorios, Reversing de Binarios (Pwn / Ret2Libc), Redes Industriales (SCADA / Modbus TCP) y Post-Explotación de entornos Docker. Todo esto impacta en una **maqueta física real** impulsada por una Raspberry Pi, con sensores láser I2C, bombas de agua (relés) y luces LED.

Evolución:
Pasamos de un script monolítico ("la licuadora") a una arquitectura pulcra de microservicios:
- `scada_web/`: Aplicación Flask corporativa, aislada en contenedores Docker.
- `nodo_raspberry/`: Servidor de borde físico (Edge OT) operando el hardware.

--------------------------------------------------------------------------------
2. LA ARQUITECTURA FINAL
--------------------------------------------------------------------------------

A) EL NODO WEB (scada_web/ en Docker)
- Aplicación Flask corriendo detrás de Gunicorn/SocketIO.
- Conectado a una base de datos MySQL en un contenedor separado (`mysqlbd`).
- IMPORTANTE: Las contraseñas de BD ya NO están hardcodeadas en `db.py`. Dependen 100% de las variables de entorno de Docker.
- Protección anti-lectura: El código de Python (`app.py`, `db.py`) está diseñado para ser ofuscado (usando PyArmor o compilado a `.so` con Cython) para que un atacante que logre acceso root en el host no pueda simplemente leer los archivos de texto para robarse las credenciales.

B) EL NODO OT FÍSICO (nodo_raspberry/)
- `rtu_daemon.py`: La mente maestra del hardware.
  - Corre en background controlando los sensores ToF (VL53L0X).
  - *Fix aplicado:* Los motores de las bombas requieren encender DOS pines de relé simultáneamente (12V y GND) para cerrar el circuito.
  - *Fix aplicado:* La librería de las Tiras LED (WS2812B) fue migrada a la C-struct de bajo nivel (`ws2811_t`) para evitar conflictos de DMA entre PWM0 y PWM1.
  - Tiene hilos (`Threads`) separados para las animaciones LED y para los semáforos. Los semáforos ahora funcionan de manera independiente (como en la calle), ignorando el estado de la planta.
- `menu_tester.py`: Una interfaz gráfica en PyQt5 creada para que tú (el administrador) puedas probar las bombas, luces y sensores físicamente saltándote la lógica del CTF.

3. LA KILL CHAIN DEFINITIVA (5 FASES)
--------------------------------------------------------------------------------
Este es el flujo exacto y obligatorio que deben seguir los jugadores para ganar:

FASE 1: Infiltración Inicial y SQLi
- El jugador llega al `login.html`. Abajo ve un formulario de "Directorio Público de Operadores".
- Ese formulario envía datos al endpoint `/api/v1/search?query=`.
- El endpoint sufre de **SQL Injection puro** (string concatenation en `db.py`).
- Usan SQLmap o UNION SELECT para dumpear la BD.
- Ven 3 usuarios: `admin_scada` (hash indestructible), `op_turno1` (hash indestructible), y la cuenta de pruebas `testing` (hash débil de `sistemas12`).
- Rompen la clave de testing con un ataque de diccionario (ej. rockyou.txt) y hacen login en la web.

FASE 2: Fuzzing y Exfiltración LFI (Pivote IT)
- Logueados como testing, la web no muestra botones útiles.
- Hacen fuzzing de rutas (`dirb`, `gobuster` con `common.txt`) y descubren `/internal/messages`.
- Leen un log de chat inventado donde el admin le dice al operador: *"Oye, te dejé tu llave SSH (id_rsa) tirada en la carpeta oculta /uploads. El usuario del servidor Debian es operador_it"*.
- El jugador usa la vulnerabilidad de Local File Inclusion (LFI) existente en el portal para robársela: `/intranet/download?file=../../uploads/id_rsa`.

FASE 3: Escalada de Privilegios (Sudo Misconfiguration / Permisos Débiles)
- Entran por SSH al servidor host como `operador_it`.
- Intentan saltarse pasos manipulando Docker (`docker ps`), pero obtienen "Permission Denied".
- Ejecutan `sudo -l` para verificar sus privilegios y ven que pueden ejecutar `sudo /opt/scripts/restart_scada.sh` sin contraseña (NOPASSWD).
- Analizan los permisos del archivo (`ls -la /opt/scripts/restart_scada.sh`) y notan un grave error: tienen permisos de escritura (el archivo pertenece a `operador_it`).
- Editan el script y le inyectan una shell al final: `echo "/bin/bash" >> /opt/scripts/restart_scada.sh`.
- Ejecutan el script vía `sudo /opt/scripts/restart_scada.sh`.
- ¡Consiguen consola `root` (`#`) en el host!

FASE 4: El Impacto Cibercinético (Sabotaje SCADA)
- Estando en el Debian como root, escanean la red y encuentran la Raspberry Pi (Puerto 502, Modbus TCP).
- Escriben un script para inyectar un paquete Modbus (Write Register 0 = 768).
- Esto desactiva los sensores de seguridad en la maqueta física. El nivel de agua llega al 100%, las bombas no paran, y la Tira LED grita en rojo: "INUNDACIÓN CRÍTICA".

FASE 5: El "Trofeo de Vuelta" (Docker Pivot)
- Para conseguir la flag final (`CtF_L1@I7uN{paS5!!_1lAItuN_@GuA}`), necesitan acceder al panel web `/admin`.
- Como el código Python está ofuscado, no pueden simplemente hacer `cat app.py`.
- Siendo root en Debian, ahora sí pueden usar comandos Docker. Hacen `docker inspect mysqlbd` y roban la variable de entorno `MYSQL_PASSWORD`.
- Entran al contenedor vivo de la BD: `docker exec -it mysqlbd mysql -u root -p`.
- Hacen un `UPDATE usuarios SET password_hash = '<nuevo_hash>' WHERE username = 'admin_scada';`.
- Vuelven a su navegador, inician sesión como Admin, y el sistema desencripta y renderiza la majestuosa Web Flag en la pantalla.

--------------------------------------------------------------------------------
4. RESUMEN DE CAMBIOS REALIZADOS EN LA ÚLTIMA SESIÓN
--------------------------------------------------------------------------------
- Hardware: Reparación de polaridad en relés de las bombas (2 pines por bomba).
- Hardware: Desacople de los semáforos a hilos automáticos independientes.
- Vulnerabilidad de Sistema: Se eliminó el reto "demasiado difícil" del Buffer Overflow en C (`plc_diagnostic.c`) y se reemplazó por un vector realista de escalada de privilegios basado en malas configuraciones de sudo (`sudo -l`) y permisos de archivos (`setup_sudo_vuln.sh`).
- BD (`db.py`): Limpieza de contraseñas harcodeadas. Se añadieron los nuevos usuarios y la ruta vulnerable `buscar_operador`.
- Web (`app.py`): Inserción del endpoint `/api/v1/search`, endpoint `/internal/messages` (con los logs de pista) y preparación del render de la Flag en `/admin`.
- UI (`login.html` & `admin.html`): Adición de la barra de búsqueda y el recuadro verde de la Flag.
- CTF Design: Se diseñó el concepto del "Trofeo de Vuelta" y el bloqueo por permisos de Docker (evitando que root sea el fin del juego).

--------------------------------------------------------------------------------
5. PRÓXIMOS PASOS (LO QUE FALTA)
--------------------------------------------------------------------------------
1. Implementar la ofuscación de Python: Compilar `app.py` y `db.py` con PyArmor o Cython para que la Fase 5 funcione y los hackers no roben la flag haciendo un simple `cat`.
2. Probar la inyección de SQLmap en el endpoint `/api/v1/search` para confirmar que se vuelcan bien los usuarios.
3. Asegurarse de que el contenedor de MySQL se levante con las claves correctas en el `docker-compose.yml`.
4. Borrar la base de datos local SQLite vieja para que se regenere con los 3 nuevos perfiles.
